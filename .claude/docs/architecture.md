# Architecture

## Layout

- `*.remote.ts`: SvelteKit remote functions, the only way pages reach the server. They sit in `src/lib/` or in a domain's folder (`src/lib/modpacks/`), never inside a `server/` folder. Every export starts with a guard (`requireUser`, `requirePermission`, `requirePanel`, `requireOwner`); `remote-guards.test.ts` enforces it in every folder.
- Domain folders: `src/lib/modpacks/` holds one domain's remotes and shared code, with its server code in `src/lib/modpacks/server/`. SvelteKit keeps any `server/` folder (and any `*.server.ts`) out of the browser. A domain with one server file names it `*.server.ts` instead of making a folder. New domains follow this; the rest still live flat in `src/lib/` and `src/lib/server/` until a change moves them.
- `src/lib/server/`: the server modules the remotes call, and what every domain shares (`db/`, `config.ts`, `auth.ts`, `http.ts`). They take an instance id and throw plain `Error`s with text meant for the user; remotes wrap calls in `userFacing`. A batch of file changes refuses an item with `ChangeRefused` (`server/http.ts`), whose `path` and `reason` (`stale` when the file changed since it was opened) reach the page as fields of the error body; pages read those, never the message text.
- `src/lib/schemas/`: valibot schemas (a `.remote.ts` cannot export them).
- `runner/`: the detached per-instance runner and its socket protocol.
- `src/routes/`: pages, plus `+server.ts` only where a remote function cannot work (real downloads, large uploads). Those use the same guards from `auth.ts`.
- Import aliases: `#lib/*`, `#runner/*`, `#test/*`.

## Where things live

- Live feeds a page follows (the console, `latest.log`): `src/lib/realtime/`, one WebSocket per tab at `/_ws`, not `query.live`, whose streams stay open until garbage collection (sveltejs/kit#16422) and use up the browser's 6 connections. The page reads `liveFeed(feed, id)` (`feed.svelte.ts`), which stops on the server once nothing reads it; the server end is `server/hub.ts` (sign-in from the session cookie, the same instance permissions as the remote functions). Production wraps `Bun.serve` from `init` in hooks.server.ts; dev runs its own socket server that Vite proxies to (`server/serve.ts`). Add a feed in `protocol.ts` and `hub.ts`. `query.live` stays for what every page shows (`listInstances`, `liveStats`).
- Anything touching a running server (state, console, RCON, stop and wait, pausing saves): `server/live-server.ts`.
- An instance's jobs (install, update, backup, restore), one at a time: `server/instance-jobs.ts`. It is the only writer of `installState` and holds busy, progress and the outcome. `start` runs a background install or update, `run` a backup or restore, `check(id, action)` says whether an action (also start and delete) may happen now, with one message per rule, and `jobState` is what pages read. Steps report progress through the `progress` callback they are given, never by instance id. Tests hold an instance busy with `holdJob` from `#test/jobs.js`.
- "May this instance's files change now?": `assertWritable` in `server/instance-jobs.ts`.
- Moving, deleting and writing files, one or many, all or none: `applyChanges` in `server/change-set.ts`. It owns safe paths, clashes, swaps, the edit checks and stale hashes; the caller passes its rules. The instance file manager calls it through `applyFileChanges` in `server/files.ts` (protected files, host code, world, busy), with `chosenPaths`, `movesInto` and `entryPath` to turn a request into changes; a pack's config files through `applyOverrideChanges` in `modpacks/server/local-packs.ts`. New folders and uploads keep their own checks in `files.ts` (`addFolder`, `uploadFiles`, `assertMayUpload`).
- The drafts of the files opened in an editor (both file editors): `FileDrafts` in `file-drafts.svelte.ts`. It loads, saves, reverts, discards and asks before leaving; each editor gives it an adapter for reading and saving. A draft keeps its editor model key when its file moves, and frees it when the file goes. The shared Discard question is `components/discard-dialog.svelte`.
- Path rules for files inside a folder (clean, inside, rebase, parent, name, join), on the page and the server: `src/lib/paths.ts`. Use them rather than writing one inline.
- The `.mrpack` format, read and written: `modpacks/server/mrpack.ts` (`readMrpack`, `writeIndex`, `safeJoin`). Nothing else opens a pack's zip or index. A pack's summary for the pages: `summarize` in `modpacks/server/modpacks.ts`, for Modrinth modpacks and builder packs alike.
- Where an instance came from: `src/lib/instance-origin.ts`.
- Modrinth dependency resolution and file picking: `server/mod-resolver.ts`.
- Showing Markdown (release notes): `components/markdown.svelte`. It draws tokens and never uses `{@html}`; keep it that way.
- Choosing a folder to move into: `components/folder-picker.svelte` is a small file manager that lists only folders, used by the Move dialogs of the pack builder and the instance file manager. The holder passes `list` (the folders inside a folder; it may be async, as the instance one is) and `exclude`; `folder-picker.ts` has the pure parts (children, exclusion, new-folder names).
- A tree of files and folders: `components/file-tree.svelte` draws it (folders open and close; each file's trailing content, such as sizes and action buttons, comes from a snippet), and `file-tree.ts` builds the nested nodes from a flat list of paths and works out where a dragged item lands (`movedPath`). Checkboxes and long-press selection are on when the holder passes `onselection` (`toggleNode`, `nodeState` and `topLevelPaths` keep a folder's choice consistent). Dragging rows to move them is on when the holder passes `onmove`, which gets the dragged paths (everything chosen when a chosen row is grabbed; `canMoveInto` says where they may land); the root is the space around the tree, so the holder takes that drop. The drag state and handlers are `drag-move.svelte.ts` (`DragMove`), shared with the instance file manager's table, which has no tree but moves rows the same way. It knows nothing about packs or instances.
- Editing text in the browser: `components/config-editor/code-editor.svelte` wraps Monaco, loaded only on first use through `config-editor/monaco.ts`; keep Monaco out of any static import. Error markers and Format for each file type: `config-format.ts` (pure, tested). What may be edited as text: `editable.ts`. A pack's config files: `readOverrideText`, `applyOverrideChanges` (every move, delete and write of one Save all, through the change set, as one revision) and `exportOverridesZip` in `modpacks/server/local-packs.ts`. The Configs panel (`pack-configs.svelte`) keeps the staged moves and deletes (`modpacks/pack-changes.ts`, pure: what the tree shows, and what to send).
- Audit: `record()` in `server/audit.ts`, written from the remote after the action succeeds. Background work captures `currentActor()` while the request is still there.
